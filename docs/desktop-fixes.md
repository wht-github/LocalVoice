# 窗口恢复与麦克风延迟排查（2026-09-06）

## 窗口恢复

Slint 1.17.1 winit 软件渲染器根据 softbuffer 的缓冲区年龄选择局部绘制。隐藏后 Windows 可能清空实际表面，但缓冲区仍被当成可复用，导致没有变化的内容不再提交。单纯 request_redraw 不会使整张表面变脏。

显示悬浮窗和设置窗口时，通过与 Slint 同版本锁定的 core 接口标记整个逻辑区域，再请求重绘；没有增加持续刷新定时器或切换渲染引擎。

回归测试读取本程序实际显示表面（不使用会主动补绘的 take_snapshot）：旧路径三次恢复每次有 465120 个字节与原画面不同；新路径三次均为 0。测试不移动鼠标。原始结果在 outputs/desktop/restore-before 与 restore-after。

## 识别延迟

原控制线程每 100 ms 执行跨应用 UI Automation 焦点检查，而且在处理停止录音/音频事件前执行。若目标应用响应较慢，电平事件每秒仍到达 10 次，控制线程可能反复等待辅助功能调用，造成停止事件与音频任务积压。这是代码层面可确认的阻塞风险；未取得用户当次慢请求的耗时记录，不能断言它是唯一原因。

修复后录音期间仅检查 Win32 前台窗口和原生焦点句柄；提交文字前保留完整控件身份与密码属性检查。UI Automation 使用支持超时的 CUIAutomation8，连接/事务各 300 ms，关闭自动设置焦点。结束录音时在同一分段锁和停止标志保护下先发送尾段，再退出 WASAPI 驱动线程。

新增有大小上限、只含时间和数值的诊断文件，以捕获实际使用时的停止、排队、编码、HTTP、推理和目标输入耗时。没有录音或文本历史。

当前服务实测（已知 6.4 秒中英测试 WAV；长样本重复四次，48 kHz 用重复采样构造计时样本，不作为音质转换实现）：

| 音频长度 | 采样率 | 客户端编码 | HTTP 往返 | 服务端报告 |
|---|---|---|---|---|
| 6.4 秒 | 24 kHz | 5 ms | 0.443 秒 | 0.397 秒 |
| 6.4 秒 | 48 kHz | 11 ms | 0.317 秒 | 0.310 秒 |
| 25.6 秒 | 24 kHz | 23 ms | 1.182 秒 | 1.189 秒 |
| 25.6 秒 | 48 kHz | 43 ms | 1.127 秒 | 1.137 秒 |

Windows 与 WSL 各自计时，数值不应用来相减推导精确网络时延。实测支持“当前测试中服务端推理和 48 kHz 路径正常”，不替代真实麦克风、驱动和用户目标应用的复测。原始报告为 outputs/desktop/asr-latency.json。没有修改模型、推理设备或 WSL 配置。

## 聊天框、终端与选区兼容

用户随后反馈 Codex 聊天框和 Windows Terminal 提示需要复制，而浏览器可用。实际控件检查发现：终端 TermControl 是 Text 控件，只暴露 TextPattern，报告 IsReadOnly=false；原判定因此拒绝它。已加入具有焦点且明确可写的终端/文档文本控件识别，并保留只读、密码、焦点变化限制。

Codex 聊天框的 ProseMirror 实际是可写 Edit/ValuePattern。直接检查以及“聚焦聊天框→点击禁用录音的诊断悬浮窗”检查均通过，原判断在这次检查中也通过，因此没有把用户的所有 Codex 失败都归因于控件类型。新增前台窗口内明确焦点控件的回退查找，提交时复核可编辑状态；真实麦克风识别后写入 Codex 尚未替用户执行。

同时排除了本轮目标应用的权限级别差异：聊天应用、Windows Terminal、Chrome 和启动工具均为 Medium（完整性 RID 8192），没有为修复而提权。

选区查找原来最多向上四层，且中间 TextPattern.GetSelection 不支持就会直接退出。现在有界查找至前台窗口，并检查前台文档提供的选区。不会读取整页来替代选区，不修改剪贴板。

验证记录：

- outputs/desktop/codex-click.json：实际聊天框点击诊断 accepted=true，未录音、未写入或发送消息。
- outputs/desktop/terminal-click.json：实际终端原判断 false，新判断 true。
- outputs/desktop/terminal-selection-click.json：专用静态终端中已知文本被选中后，点击真实朗读按钮，读回内容匹配，约 19 ms；未播放声音。
- Codex 的自动选区构造未通过：外层文档 FindText/Select 后，提供者读回的内容与查找词不一致；通过已知段落名称定位也没有得到单个对应节点。未将这些测试标为成功，也未以其证明鼠标选区一定失败。实际鼠标选区仍需用户复测。

新增两项可编辑性回归，覆盖可写终端/文档、只读与属性未知的控件。应用控件接口差异仍存在，不能承诺所有应用都支持自动输入和选区读取。

## 2026-09-06：结束时选定输入目标与连续朗读

用户反馈前一版输入更不稳定后，诊断日志显示三次短录音的 HTTP 识别约 0.126、0.152、0.283 秒，最终输入均失败；旧日志没有具体拒绝原因，不能将每次失败都认定为同一个原因。

本次变更：
- 开始时不再检查密码框或绑定任何输入控件；手动结束立即记录前台 HWND、进程和原生键盘焦点，随后停止音频采集。
- 不再以 UIA 的编辑接口、可写属性或 CompareElements 对象身份作为输入前提。输入时核对原生目标，已知密码框仍拒绝输入；不会主动抢回窗口或发送 Enter。
- 识别过快、结束快捷键仍按住时，将结果留在控制器内等待释放；事件循环继续处理取消和退出。输入失败日志增加原因，未记录转写文字。
- 朗读短文本不按每句、每个换行拆请求。长文本仅为资源上限打包到最多 180 字，播放时预取后续音频，共用一个 Sink，最多当前音频加一份后续缓存。音频线程独立响应取消，即使下一次 HTTP 合成仍在等待也能停止播放。

验证：17 项单元测试通过，包括预取时机、满缓存不继续请求、HTTP 合成期间音频响应取消。发布版专用窗口验证标准输入框、切换后目标及无 UIA 编辑接口的自绘输入框均能输入；错误原生焦点被拒绝。真实 TTS→ASR 回环与三次隐藏恢复检查通过。报告见 `outputs/desktop/native-check.json`、`service-check.json` 和 `restore-regression/result.json`。

测试没有录制真实麦克风、播放扬声器或向用户的 Codex/终端输入；这些真实界面的完整交互仍需使用时确认。SendInput 成功表示系统接受了输入事件，不等价于应用已经显示文字。模型、WSL 配置和服务资源限制未修改。

## 连续听写模式（2026-09-06）

设置新增“连续听写（停顿后输入，直到手动停止）”。默认保持手动模式，保存后下一次开始说话使用新模式，当前会话的模式不会中途变化。

连续模式复用现有麦克风和 ASR 服务：约 700 ms 停顿后提交，一直说话时每份音频不超过 25 秒。麦克风保持运行；每次结果准备输入时重新取得前台原生键盘焦点，按识别顺序交付。快捷键未释放的多份结果使用队列保留，不覆盖前一份。普通结束补交尾部音频，取消使尚未完成结果失效。

单次无可输入目标或识别失败会提示，但继续听写；未送达文本仅保留供复制。正在识别、等待识别与等待输入合计最多三份；积压会暂停录音。待复制文本超过 256 KiB 时也暂停并提示。无新增模型、服务或全局 WSL 配置。

自动验证新增：旧配置默认手动、连续模式保存往返、多次停顿持续产生结果、停止补交尾音、50.1 秒连续发声按 25+25+0.1 秒有界处理且不丢弃短尾部。手动模式 52 秒录音保留全部内部停顿的既有测试仍通过。

本次发布验证：20 项单元测试通过；专用标准/自绘输入控件检查通过；三次隐藏恢复像素差均为 0；新增设置开关与保存按钮布局完整。新版客户端已启动，ASR health 为 ready。用户当前设置 tts_enabled=false，TTS 回环检查因服务关闭未完成，未为测试重新开启朗读。未采集真实麦克风或向真实聊天框写入。

## 2026-09-13：分辨率变化后显示不全

此前完整重绘只覆盖隐藏后恢复。Windows 的 `WM_DISPLAYCHANGE` 没有被当前 winit 暴露为窗口事件；分辨率切换导致实际表面丢失时，软件渲染器可能仍把缓冲区视为可复用。窗口位置也只在首次显示时按屏幕大小计算，屏幕变小后可能留在可见区域之外。

修复同时应用于悬浮窗和设置窗口：

- 接收 `WM_DISPLAYCHANGE` 并请求绘制，记录显示变化序号。
- 尺寸、DPI、遮挡恢复事件先交给框架正常处理，在随后的绘制开始前用最新逻辑尺寸标记整个表面。这个绘制钩子不再次请求绘制，避免产生重绘循环。
- 显示变化后按最近显示器的工作区修正窗口位置，不激活窗口。窗口大于工作区时保留左上角可达；不强制改变用户的 DPI 或缩小字体。

对照中的正常 DPI 换算原本就通过，因此继续使用 winit 的标准尺寸计算，没有增加自定义缩放公式或替换渲染后端。

新增 `--display-check`，用程序自己的窗口和 GDI 实际表面做验证。100%、150%、200%、恢复原 DPI，再分别测试表面丢失与越界；两个窗口共 12 个场景。表面丢失场景不同时移动窗口，越界场景不同时擦除画面，以分开检查重绘和位置恢复。参照图在采集实际表面后才显式完整重绘，不使用会主动补绘的 Slint snapshot 作为实际图。

关闭修复时，表面丢失后的悬浮窗有 116280 个字节、设置窗口有 862818 个字节与完整画面不同；两个越界场景均未自行回到工作区。原始对照在 `outputs/desktop/display-before-final/result.json`。

最终发布版 12 个场景全部通过：实际表面与完整重绘的字节差均为 0，尺寸和位置检查通过，报告在 `outputs/desktop/display-after-final/result.json`。既有三次隐藏／恢复检查也均为 0 字节差（`outputs/desktop/display-restore/result.json`）。23 项单元测试通过，包含负坐标显示器、正常位置不移动和窗口大于工作区时的边界检查；发布版已重启，保留原来的 1.7B Q8 模型设置。

测试发送的是合成 Windows 消息，并非真的切换系统分辨率或插拔显示器；它验证显示恢复路径，不能等价为所有显卡驱动、远程桌面、多显示器组合的实测。代码与构建依赖均留在仓库，没有修改 Slint/winit 的全局缓存源码。
