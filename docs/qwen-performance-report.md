# Qwen ASR 实际推理瓶颈与下一项修改

测量日期：2026-09-09。本机 RTX 4050 Laptop GPU，Qwen3-ASR-0.6B-hf，PyTorch 2.9.1+cu128、Transformers 5.16.1，FP16、SDPA、batch=1、贪心生成、自动语言、最多 1024 个新 token。保持当前桌面实现的推理参数；本次没有替换模型算子。

**结论：优先优化文本逐 token 解码。推荐从宽度 1024 的 RMSNorm 融合开始，之后必须回到完整转写验证收益。**

## 1. 无 Profiler 的转写基线

每个输入预热一次后测 3 次；此前还测了一次冷请求。表中为中位数。计时是进程内的预处理、GPU 传输、完整生成和文本解码，不含文件加载、录音、HTTP 或桌面文字输入，因此不是按下快捷键到文字出现的完整延迟。

| 输入 | 音频长度 | 转写时间 | 三次耗时范围 | 输出 token |
|---|---:|---:|---:|---:|
| 中文前 3 秒截取 | 3.00 s | 1.041 s | 0.969–1.048 s | 17 |
| 完整中文 | 10.42 s | 1.923 s | 1.737–2.080 s | 41 |
| 中英混合 | 12.59 s | 1.794 s | 1.784–1.810 s | 43 |
| 中文 + 0.5 秒静音 + 中英混合 | 23.50 s | 3.309 s | 3.276–3.325 s | 80 |

模型和处理器加载耗时 2.82 秒（不含解释器启动及库导入）；第一次完整中文请求耗时 4.20 秒。所有样本的 3 次热运行识别结果各自一致，均正常结束，没有触及 token 上限。

热运行预处理约 2.5–6.1 ms，传输约 0.4–0.6 ms，文本解码约 0.2–0.5 ms。生成占各样本总耗时超过 99%，所以先改音频预处理并不能解决主要延迟。

这些输入来自已有的合成语音文件 `outputs/melo-mandarin.wav`、`outputs/melo-mixed.wav`。短句是直接截取，长音频是拼接；它们适合建立性能基线，不构成真人麦克风识别准确率测试。未锁定 GPU 时钟或功耗，不能将小幅耗时差异过度解释。

## 2. 完整中文转写的 GPU 时间线

独立采集一整次转写：1 次音频编码、1 次文本 prefill、40 次文本 decode。Profiler 与模块标记会影响执行和提交耗时，以下数据只用于定位热点，不能与上表直接相减或相加。

共采集 84,034 次 GPU 内核执行，累计 GPU 内核时长约 482.63 ms。84,033 次可关联到 CPU 算子事件；模块 GPU 归属依据关联算子的提交时间及模块标记区间计算。

| 部分 | GPU 内核累计时间 | 占本次所有 GPU 内核时间 |
|---|---:|---:|
| 音频编码器 | 8.34 ms | 1.7% |
| 文本 prefill | 18.22 ms | 3.8% |
| 文本逐 token decode，40 次 | 374.79 ms | 77.7% |
| 输出词表投影，位于文本模型外 | 79.02 ms | 16.4% |

余下是投影、采样等其他工作。GPU 内核累计时长不包含内核之间的空隙，也不等于整个请求耗时。解码包含大量小算子和提交工作；是否能减少整体等待，需要无 Profiler 的 A/B 实测确认。

## 3. 候选修改点

此表与上面的阶段表有重叠，不可相加。

| 候选 | 测得的 GPU 累计时间 | 判断 |
|---|---:|---|
| 所有 `aten::mm` 矩阵乘法 | 298.94 ms，61.9% | 最大的计算类别，但已使用库内核；涉及多种形状，首个模型练习直接超越它难度较高 |
| 输出词表投影 `[1,1024] × [1024,151936]` | 79.02 ms，16.4% | 明确热点；量化或专用 GEMV 值得后续评估，暂不作为第一项改写 |
| 全部 RMSNorm | 66.34 ms，13.7%；4,633 次模块调用 | 每次展开为约 8 个 GPU 内核，有归约、类型转换和逐元素融合空间 |
| 单独 SiLU 激活 | 2.03 ms，0.4% | 虽然容易写，但孤立替换收益很小；不继续做另一个脱离整体目标的激活练习 |

RMSNorm 的 CPU 模块范围在 Profiler 下累计约 1.21 秒，但这些范围受到标记开销影响，且与 GPU 重叠，**不能把它当成可节省的真实转写时间**。

## 4. 推荐：先改宽度 1024 的 RMSNorm

实际代码在当前环境的 `transformers/models/qwen3/modeling_qwen3.py`，`Qwen3RMSNorm.forward`，第 59–64 行。模型有 28 个文本层：每层的 `input_layernorm` 和 `post_attention_layernorm`，以及末尾 `norm`，共 57 个该宽度模块。

本次实际输入形状：

- prefill：`[1,151,1024]`，57 次；151 是这条录音的 prompt 序列长度，其他录音会变化。
- decode：`[1,1,1024]`，2,280 次，即 57 × 40。
- 输入和权重为 FP16，沿最后一维使用 FP32 计算平方和与归约，epsilon 为 `1e-6`。

这些模块合计 2,337 次调用，关联到约 18,695 次 GPU 内核执行，累计 32.25 ms，占所有 GPU 内核时间约 6.7%。将它们变成一次调用一个融合内核，既有实际模型接入点，也能学习归约，而不必同时处理 Q/K norm 的多维布局。

参考计算顺序：

```python
input_dtype = x.dtype
xf = x.float()
variance = xf.pow(2).mean(-1, keepdim=True)
normalized = xf * torch.rsqrt(variance + 1e-6)
y = weight * normalized.to(input_dtype)
```

注意：参考代码先把归一化结果转换回 FP16，再乘 FP16 权重。若融合实现全程计算到最后才转 FP16，舍入顺序会不同。应先保证误差可接受，再测整段识别；不要在第三方安装目录里直接改源码。

建议将实现作为项目内可选替换，仅覆盖上述宽度 1024 的模块；默认继续走原始 PyTorch。测试应包含真实形状、不同幅值、零输入，比较数值误差，然后使用本报告的同一组录音比较文本、输出 token 数和热运行总时间。核心 TileLang 计算留给你动手。

**收益边界：** 即使完全消除这些模块的 GPU 计算，本次采集中也只减少约 32.25 ms 的 GPU 内核时间；只看内核累计时间，对应理论上限约 1.072 倍。融合还可能减少提交开销，但其整体收益尚未测得。全部 RMSNorm 的相应 GPU 时间上限约 1.159 倍。这些都不是端到端加速承诺。若整段转写没有稳定变快，就不继续扩大这条优化。

## 5. 复现和数据

```powershell
.\.venv-qwen\Scripts\python.exe -X utf8 scripts/profile-qwen.py
.\.venv-qwen\Scripts\python.exe -X utf8 scripts/analyze-qwen-trace.py outputs/qwen-profile/<时间戳>/mandarin.trace.json
```

本次原始数据目录：`outputs/qwen-profile/20260909-234752/`。

- `baseline.json`：3 次热运行的分阶段时间、冷请求、完整识别文本。
- `mandarin.trace.json`：完整时间线，约 225 MB。
- `trace-analysis.json`：按真实输入形状汇总的 GPU 算子时间，以及模块归属。

首次采集在时间线成功写盘后，调用 Profiler 的 `key_averages()` 汇总时占用超过 11 GB 内存；已停止该分析进程，保留有效时间线。现在使用逐事件读取的独立分析脚本，不再展开 PyTorch 事件树。未停止桌面识别服务。本次没有生成最初脚本末尾的 `profile.json`，模块次数和形状来自已保存的完整 trace；修订版将先保存该附加元数据，再导出 trace。
