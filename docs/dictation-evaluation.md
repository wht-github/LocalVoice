# 中英术语、轻整理与笔记评测

`scripts/evaluate-dictation.py` 是小型离线评测入口：向已运行的本地服务发送明确提供的音频或文本，保存逐例结果、指标和人工审阅表。使用 Python 标准库，不录音、不下载模型、不启动或停止应用服务，也不修改日常日志。

它回答三个问题：不维护词表时，主力 ASR 能否听对日常中英混合技术表达；整理能否减少人工修改而不改变原意；笔记能否保留完整意思并方便保存。产品目标见 [下一版规划](product-roadmap.md)。

**空词表是首要质量门槛。** 常见计算机术语、英文名称和常用音译表达，应由基础模型与当前语句上下文识别，不能把逐词维护纠错表当作日常使用前提。先评估 `terms=[]` 的原始 ASR，再评估同样不带词表的轻整理与笔记；原始识别不合格时，应继续比较模型，不能用预先列出答案或后处理改词宣称识别问题已解决。个人词表仅是内部项目名、自定义缩写等专名的可选辅助，其收益另外报告。

## 当前素材与边界

仓库的 [文本开发集](../tests/fixtures/dictation/cases.text.jsonl) 包含 8 条合成文本，以及用户提供的 AGV / blueprint / UE / transition 口述原文和同源笔记检查用例。它们用于整理回归，**不是语音 benchmark**。尚未收集个人真实音频、建立冻结验收集或测出模型的术语准确率。

AGV 的两个 case 使用相同文本，只是人工检查重点不同，不能算作两个独立场景。`source` 与 `derived_from` 会随输入清单写入评测目录，审阅时可识别来源。

用户举出的 `model`、`AGV`、`Unreal`、`shader`、`blueprint`、`UE`、`transition` 是实际使用线索，不是封闭的识别词汇范围。把这几个词固定写入提示后识别正确，不足以证明模型能处理后续自然说出的术语。文本开发集也无法验证中文口音的英文发音或中英文切换能力。

脚本直接调用 HTTP 接口，不经过桌面录音、25 秒切分、队列、焦点检查和文字输入；`total_request` 不代表说完至上屏耗时。当前音频请求限制仍由服务端决定，长笔记的分块完整性和桌面体验需要另外做完整应用验收。长篇整理可用 `text` case 隔离验证。

## 2026-10-18 前一轮文字开发验证

前一轮先用文字排除明显不合格的整理候选，没有测技术口述识别准确率。全部使用空词表，结果逐句核对；HTTP 200 仅表示请求完成。以下保留当时的开发决策；最新轻量要求下的选型结论见后面的资源对比，不再推荐 4B 作为默认辅助层。

| 候选与提示版本 | 实际发现 | 决策 |
| --- | --- | --- |
| Qwen3-0.6B Q8，早期探索 | 漏否定、把待执行请求变成已完成等 | 不选用 |
| Qwen3-1.7B Q8 | 24 次请求中出现 attention 算子误改、笔记漏否定和导入对象 | 不选用 |
| Qwen3.5-4B Q4_K_M，边界修复前 | 24 次请求中一条笔记只输出口述引用中的 OK，丢掉待记录内容 | 修复通用数据边界，不针对词句加替换规则 |
| 同一 4B，JSON 数据边界 v2 | 30 次请求中原问题与新增引用变体得到修复，但一条笔记丢失“明天”的时间限定；其余 29 次未发现关键语义遗漏 | 日常输入可选，笔记标为试用；不声明通过完整保真验收 |

最终这组共 14 个不同文本：10 条仓库 case 中 AGV 原文重复一次，另外增加 2 条未登记术语／问题用例和 3 条引用边界变体，每条同时跑 clean 与 notes。新增变体用于开发检查，不能算未接触过的冻结验收集。轻整理仍保守，例如用户 AGV 句还保留“那个／给我”；没有测得必要修改量下降 30% 的产品目标，也不把英文名词在文本中保留视为 ASR 听对。

最终模型为 Unsloth Qwen3.5-4B Q4_K_M，revision `b0bd07786f94b700012140fd9263b2de83d4f97b`，16 GPU 层、8192 上下文，非思考模式。提示摘要为 `b111baafab972fdfe13ab7e495d812fa9c289113a4c25f576cf02c70d69d9f46`。第一次整理含加载 4.41 秒；其余 clean 请求中位数 2.42 秒、最大 3.10 秒，notes 中位数 2.94 秒、最大 3.94 秒。每个短文本只执行一次，这些数值不是多次重复的稳定性能基准，也不含音频识别和桌面交付。

Qwen ASR 1.7B 单独驻留时整卡显存快照约 3277 MiB，和文字模型共驻约 5080/6141 MiB。这是请求间的采样，不是连续监测的峰值；未验证 UE 同时工作。两秒公开音频在文字模型加载前后转写一致，只证明共存链路可用，不代表个人技术语音质量。

原始报告保存在本地忽略目录 `outputs/text-live-empty-terms-qwen3.5-4b-boundary-v2.json`，人工复核在 `outputs/text-live-qwen3.5-4b-boundary-v2-review.json`；旧失败报告保留。显式开发检查 `tests/check_text_http_live.py --output <新报告路径>` 会启动自己的随机端口 ASR 服务，使用已经安装的模型与公开音频，跑完关闭所属进程；不读取日常转写历史，也不采集麦克风。它有别于下方仅连接既有服务的评测脚本。

交互验证另有 26 项 Rust 测试通过、16 项 Python 单测通过，以及 12 个 UI 状态的渲染检查。它们覆盖协议、失败保留原文、取消后不交付和界面布局，不替代上述语义检查。原样模式保持默认；笔记只能预览和复制，保存前核对原文。后续先保留“明天”遗漏为回归项，再用真人短句、30 秒至 3 分钟笔记及独立冻结集决定是否达到发布标准。

4B 的整卡显存从整理加载前 3433 MiB 到采样最大 5391 MiB，差约 1958 MiB；该配置在 CPU 和 GPU 上都保留部分模型。CPU 候选无 GPU 层，整卡差值约为 0，出现的 8/17 MiB 波动不能从整卡计数归因到模型。各模型推理时平均约 3.9–4.0 个逻辑核忙碌，CPU 路线仍会争用处理器和内存带宽。

这些结果说明参数量与文件体积都不足以代表运行占用。例如 0.6B Q8 在此上下文配置中的工作集比 1.2B 混合架构 Q4 更大。不能把复制原文、漏掉大量内容或被截断的输出算作“低延迟且质量好”。主对照只反映应用当前固定提示下的表现，不证明模型在所有中文任务上都同样失败。

### 去除提示示例的单因素消融

主对照发现部分小模型把提示中的“选择 B／先别部署／测两次”抄进无关笔记。因此对三款新候选再跑同样 29 次请求，只去掉中间一组 user/assistant 示例。保留系统规则、JSON 数据边界、输入、空词表、上下文与采样配置；没有逐个模型反复调提示。

| CPU 候选，无示例 | 工作集采样最大 MiB | 短句秒 clean / notes | 长笔记秒 | 是否解决主要问题 |
| --- | ---: | ---: | ---: | --- |
| Qwen3.5-0.8B Q4 | 1144 | 1.59 / 1.76 | 8.95 | 否。clean 仍 12/14 原样复制；notes 将“不要先改 temporal upsampling”扩写成优先调整它，另一例重复至截断；长段直接复制，没有组织 |
| LFM2.5-1.2B Q4 | 1532 | 1.85 / 2.07 | 8.04 | 否。把“不是计算量不够”反写，引用用例仍只回 OK；长段丢数字、版本、条件和未确认事项 |
| LFM2.5-350M Q4 | 691 | 0.90 / 0.81 | 1.66 | 否。把 AGV 导入与坐标标注写成已完成，把 6 GB 写成“6瓶”；长段将最终每秒 12 改回 20 |

去示例减少部分污染，却没有消除独立的语义错误。全部九种配置共 238 个输出，由逐条审阅区分生成截断、改义／编造、时间或条件遗漏、术语翻译，以及仅格式变化或没有整理收益；分类可以重叠，不相加制造一个笼统“准确率”。其中八组各 29 个输出，1.7B 只有 6 个筛选输出。

本轮结论：**没有可直接替换为默认整理模型的小模型，4B 的成本也不适合默认辅助层。** 这不等于证明小模型做不到，而是当前通用指令方案未达到要求。下一步先把保守格式清理作为明确有限的能力，并验证文字模型按需加载、空闲卸载；笔记继续预览，不把质量风险带入自动输入。若继续研究小模型，固定资源预算，单独验证任务专用编辑或训练能否带来收益；每次与原文及规则对照，只在独立数据上通过保真和修改量门槛后采用，不继续靠增大模型解决问题。本轮未更换生产配置，也未实现空闲卸载。

### 测量口径

最新需求不接受为辅助整理常驻较大模型。本轮以现有 4B 配置为对照，增加 Qwen3.5-0.8B Q4_K_M、LFM2.5-1.2B-Instruct Q4_K_M、LFM2.5-350M Q4_K_M 三个 CPU 候选，并重新测已有 Qwen3-0.6B / 1.7B Q8。Qwen0.8 为 Unsloth 的第三方量化；LFM 两款为 LiquidAI 官方量化，使用其自定义模型许可，不能统称为 Apache 模型。[Qwen 模型卡](https://huggingface.co/Qwen/Qwen3.5-0.8B)、[Qwen 量化文件](https://huggingface.co/unsloth/Qwen3.5-0.8B-GGUF)、[LFM1.2 官方量化](https://huggingface.co/LiquidAI/LFM2.5-1.2B-Instruct-GGUF)、[LFM350 官方模型](https://huggingface.co/LiquidAI/LFM2.5-350M)。

本机环境为 Windows 11、Ryzen 7 7840H（8 核 16 线程）、系统报告约 30.69 GiB 物理内存、RTX 4050 Laptop（6141 MiB）。所有文字模型固定 8192 上下文、4 个线程、关闭提示缓存、temperature 0、空词表。主对照沿用上文 boundary-v2 提示；三款新小模型另做一次去除示例的消融，只删除中间 user/assistant 示例，不改其余规则、采样参数和输入。量化、架构及 GPU 分配并非全部相同，所以这是应用配置对比，不能单独归因于参数规模。

每个完整配置使用去重的 14 个短文本，各跑 clean/notes，再增加一条 755 字符的合成长笔记，共 29 次请求。长段含 12 项人工核对要点，覆盖明天上午、周五仅为期望、20→12 纠正、动作顺序、条件、未完成状态和待回听的英文词；不是用户录音，也不是独立冻结验收集。已有 1.7B 仅跑 3 个输入的 6 次请求作资源筛选，不能与完整组比较质量率。每段只运行一次，耗时中位数是不同文本的汇总，不是重复基准；生成被截断或内容缺失的快输出不能算合格的速度成绩。

采样对象是测试自行启动的 llama-server 子进程。文字模型和 ASR 的 PID 分开统计；ASR1.7 在整理期间驻留但空闲。约每 200 ms 采集工作集、私有提交和 CPU 时间，整卡显存读数约每 500 ms 更新，实际间隔还受查询耗时影响。工作集含映射权重及共享页面，不能直接相加视为物理内存；私有提交也不等于实际驻留 RAM。报告中的最大值是采样最大值，不是连续硬件峰值，不包括桌面客户端与 Python 适配器。CPU 时间除以墙钟时间得到平均忙碌的逻辑核数。

CPU 候选配置为 `--device none -ngl 0`，整理没有 GPU 层；整卡仍有 ASR 与用户桌面占用。测量期间后台显存从约 340 MiB 变化到约 153 MiB，不能把 CPU 组出现的几 MiB 差值误认为整理模型显存。加载耗时为新模型进程启动到 ready，不清操作系统文件缓存，不能当作重启电脑后的冷启动。各组结束关闭所属模型进程，并记录释放后的快照；不停止用户服务、不录音、不向其他窗口输入文字。

无模型对照只删除句首或句后、被逗号独立分隔的“嗯／呃”，并规范未引用片段中的中英空格。14 个短文本中 4 个发生变化，其中 2 个只是格式变化；其余 10 个不变。短文本与合成长段未见关键内容被改，但保留了“那个／给我／一下”、口头纠正和强调重复，不能代表完整去口语，更不能替代结构化笔记。它没有模型权重或模型 GPU 分配；规则函数的微秒级耗时不等于完整应用延迟。

### 复现与原始证据

[资源基准脚本](../scripts/benchmark-cleanup-resources.py) 使用仓库固定文本与 [资源扩展用例](../tests/fixtures/dictation/resource-cases.jsonl)，不从旧评测结果提取输入。它依赖 Windows、现有 Python 环境、已安装的 llama.cpp 与 nvidia-smi；自行启动随机端口的模型进程并在结束后关闭，不连接或切换用户正在使用的服务。它与下方仅连接既有服务的 `evaluate-dictation.py` 用途不同。

```powershell
.venv\Scripts\python.exe scripts/benchmark-cleanup-resources.py --validate-cases
.venv\Scripts\python.exe scripts/benchmark-cleanup-resources.py --text-model .runtime/models/Qwen3.5-0.8B-GGUF/Qwen3.5-0.8B-Q4_K_M.gguf --device cpu --asr 1.7b --output outputs/resource-new-baseline.json
.venv\Scripts\python.exe scripts/benchmark-cleanup-resources.py --text-model .runtime/models/Qwen3.5-0.8B-GGUF/Qwen3.5-0.8B-Q4_K_M.gguf --device cpu --asr 1.7b --without-example --output outputs/resource-new-without-example.json
```

模型文件及相邻 `manifest.json` 必须已经存在，脚本不下载。输出路径不得已存在。`--asr none` 可单测文字模型；`--asr 0.6b` 可比较较小识别模型的共存成本；GPU 对照显式使用 `--device cuda --gpu-layers 16`。运行期间不要同时做其他模型基准。短句和长段均为开发素材，不能将复跑视为新增独立样本。

本机保存的证据均在忽略目录 `outputs/`，不随应用分发：

- `cleanup-resource-summary.json`：九种配置与两个 ASR 的资源汇总，逐行指向原始报告。
- `cleanup-resource-quality-review.json`：按用例和模式记录的语义审阅，以及无模型对照的能力边界。
- `cleanup-resource-*-cpu.json`、`cleanup-resource-*-cpu-without-example.json` 与 `cleanup-resource-qwen35-4b-gpu16.json`：模型标识、提示哈希、原始输出、耗时、采样与进程清理结果。
- `cleanup-resource-rule-baseline.json`：保守规则对照的逐例输出。

最初六组由临时脚本产生，随后将同样输入和生成参数归档到上述资源脚本；三组去示例消融使用归档脚本。各报告保留当次脚本哈希，不能声称它们来自完全相同的脚本文件。最终用例校验、脚本编译、提示哈希核对通过；全部自启模型进程已退出。生产代码未在本轮更改，之前的桌面单测成绩也不算作本轮模型质量证据。

## 新一轮专用口语整理模型调研（2026-10-18）

用户进一步明确：识别层先沿用 SenseVoice 或 Qwen3-ASR 1.7B，重点是在笔记模式把识别后的口语整理为连贯正文。第一阶段只要求删除无意义重复、解决明确改口、补断句和局部连接，保留原意与细节；摘要、提炼结论和强制待办结构另行评估。前一轮通用模型失败不能推导出任务专用小模型也不可行；保守规则仍是资源和保真对照，不能替代用户要的连贯表达。

这一调研阶段只核实公开资料、权重文件元数据与推理协议。随后已按用户要求完成前两个候选的本机测试，结果见下方“两个专用模型的实际测试”；以下表格保留调研时的候选顺序。文件体积均为十进制，不代表 RAM；Granite 与 Qwen3.5-2B 仍未实测。

| 后备 | Qwen3.5-2B | 2026-03-02；2B | Unsloth Q4_K_M GGUF 1.28 GB | 已测 0.8B 与 4B 的中间档，但超过建议文件预算；不先扩展这一档 |

### 第一候选：AgenticASR-Refiner

作者发布了独立的文本 Refiner，处理口癖、重复、自我修正和书面形式，明确支持中文与英文，并提供整段离线推理。可复用本项目的识别与结果视图，首轮不需要引入其流式代理系统。代码和原权重页均标注 Apache-2.0；官方也提供 MLX int4、ONNX int4 变体，但这不等于当前 Windows llama.cpp 已经验证兼容。[作者仓库](https://github.com/AnXMuy/AgenticASR)、[原权重](https://huggingface.co/Andrew0425/AgenticASR-Refiner)。

论文用 MiniCPM-5-1B 作基座，训练输入目标对为 10 万条，训练最大长度 1024 tokens。AASR-Bench 有 917 条中英样本，包含技术和编程场景，并评价中英混合文本；约 84% 音频为合成，不能外推为用户自然口述、未登记 UE 术语或长笔记的保真结果。文中 Qwen3-ASR 1.7B 加 Refiner 的 Overall 79.95 是作者评分体系的分数，不是逐条成功率；9.59 秒是整条 ASR 加整理的 CPU 均值，也不是本机纯整理延迟。[论文](https://arxiv.org/html/2607.28175v1)。

可用的 MigoXV 社区 GGUF 文件为 688,065,792 bytes，SHA-256 `1dcbbbfde39742b213101c0d5fe645bfda18e5c9b693409205c481efbb487758`，检查时 revision 为 `2680cd2ec627e7ae61d9288b5d6f314cb6af2e6a`。发布者明确没有提供完整转换记录、量化质量对照或端到端命令实测，因此先核对 tokenizer、聊天模板和停止条件再测质量。128k 上下文元数据不代表已验证长篇整理。模型输出还可能附带 `<KEY>` 实体标记，交付纯正文时需要单独处理，不能将标记直接输入用户笔记。[量化发布说明](https://huggingface.co/MigoXV/AgenticASR-Refiner-GGUF)。

### 第二候选：MyVoiceTyping-1.5B

这个模型基座较旧，但面向中文 ASR 后处理的专用发布较新。作者用 Qwen2.5-1.5B-Instruct 做 LoRA 微调，训练目标包含断句、口语重复、句意不顺与中英术语，支持 note/coding 等场景标签。它可以作为现有 llama.cpp 的文字模型候选，应用本身是 macOS 不妨碍单独评估 GGUF。应使用作者的训练输入协议，不能直接套前一轮通用提示判定能力。[模型使用说明](https://github.com/botaruibo/MyVoiceTyping/blob/main/docs/MODEL.md)。

ModelScope 文件 API 核实大小为 986,048,544 bytes，即 986 MB／约 940 MiB；权重文件 revision `3be3b98d9f1e4c784f708ead10d09bcb7290531d`，SHA-256 `84ade41901b3106f4e0ab3af9eec61c35e4d8ff22add8aa5c19f98aa7bc3bfc2`，模型页标注 Apache-2.0。模型卡自报训练长度 512、测试集 2506 条；它承认长口语断句和强润色受限。当前公开文件树没有模型卡列出的完整 evaluation 目录，因此不把自报综合分当作可复现验收，更不能据此声称比上一轮 4B 更好。[模型页](https://modelscope.cn/models/botaruibo/MyVoiceTyping-1.5b-q4)、[公开文件元数据](https://modelscope.cn/api/v1/models/botaruibo/MyVoiceTyping-1.5b-q4/repo/files?Revision=master&Recursive=true)。

### 为什么不继续堆通用候选

Granite 4.0 H-1B 明确支持中文，但官方也说明指令训练主要为英文；Qwen3.5-2B 默认非思考，体积则超出当前建议预算。它们可作通用模型对照，优先级低于上述任务专用模型。[Granite 模型卡](https://huggingface.co/ibm-granite/granite-4.0-h-1b)、[官方 GGUF](https://huggingface.co/ibm-granite/granite-4.0-h-1b-GGUF)、[Qwen 模型卡](https://huggingface.co/Qwen/Qwen3.5-2B)、[量化文件](https://huggingface.co/unsloth/Qwen3.5-2B-GGUF)。

FormalASR 0.6B／1.7B 是音频直接生成书面语的另一条路线，不是可挂在既有转写后面的文字模型，本轮不因此更换 ASR。FluidVoice 的本地增强层目前由作者私有维护，不能把应用开源等同于整理模型权重开放。Gemma 4 E2B 的有效参数标签也不能直接代表资源体积，其 Q4 文件约 3.11 GB，不符合本轮轻量方向。[FormalASR 作者权重](https://huggingface.co/TaurenMountain/FormalASR-0.6B)、[FluidVoice 说明](https://github.com/altic-dev/FluidVoice#fluid-intelligence)、[Gemma 规格](https://ai.google.dev/gemma/docs/core/model_card_4)、[Gemma 量化文件](https://huggingface.co/unsloth/gemma-4-E2B-it-GGUF/blob/main/gemma-4-E2B-it-Q4_K_M.gguf)。

### 调研时拟定的验证方法

固定同一份转写、空词表和本机资源设置，先测 AgenticASR-Refiner，再测 MyVoiceTyping。把“连贯正文”和“摘要／结构化笔记”分开，先判断正文是否更容易直接使用。保留旧开发集中的数字、时间、否定、英文名称、引用和待办状态检查，另加自然段级的重复、改口和句间连接；新独立样本不用于调提示。

先按各自训练协议跑通，再做一次简洁正文提示的单因素消融；同时给通用基座使用相同任务定义，以免把任务变化的收益全算给微调。仅在上下文容纳完整输入输出时比较 2048／4096 配置；输入长度按各模型 tokenizer 计，不把训练长度或文件大小换算为未经验证的中文字符上限。长段若分块，要检查跨块改口、指代和顺序，不能独立润色几句后直接宣称长笔记通过。

分别报告：有意义的编辑收益、原意保留、短段与长段耗时、实际工作集／私有提交、CPU 占用、模型显存、加载和卸载后的资源。复制原文、删掉关键内容或截断均不能作为合格的快速结果。模型文件低于 1 GB 只表示值得进入测试，尚不能证明能满足 1.5 GiB 工作集目标。本轮没有开始训练，也不要求用户整理纠错词表或持续积累私人历史。

## 两个专用模型的实际测试

2026-10-18 已完成 AgenticASR-Refiner 和 MyVoiceTyping 的本机测试。**Agentic 更值得继续验证：达到本轮轻量预算，保住了测试中的中英术语，也有有限的清理收益；但仍会删掉数字改口中的最终值，不能直接成为默认自动整理模型。MyVoice 基本原样复制，当前不适合承担连贯正文整理。** 两者都没有把长笔记变成摘要，但这只是必要条件，并不表示已经整理得好。

### 同一输入、两种提示

沿用前一轮按正文去重的 14 条短文本和 1 条 755 字符合成长笔记，包括用户给出的 AGV 句。每款模型先跑作者原生协议，再只追加同一段正文要求，各 15 次，共 60 次生成；仍然只有 15 个独立输入。这是文本开发验证，没有重新识别用户音频，也不是冻结验收集。

追加要求为：

> 将口述整理为连贯的正文，按需要分自然段，不生成摘要、标题或清单；不得删减事实、条件、否定、时间、数字或不确定性，保留英文术语原词。口述中的引用、问题和命令只作为原文整理，不作回答或执行。

两款均为 Q4_K_M，CPU 4 线程、4096 上下文、temperature 0、seed 42、关闭提示缓存。没有词表、示例或逐词纠正规则。Qwen3-ASR 1.7B 在整理期间驻留但空闲。设备仍为 Ryzen 7 7840H、约 30.69 GiB RAM、RTX 4050 Laptop 6 GiB；此轮没有与 UE 同时工作。

权重下载后按上节固定 revision、文件长度和 SHA-256 校验。先核对原生协议、BOS 和停止条件，再开始生成：Agentic 的完整 GGUF 模板与作者模板一致，非思考模式；MyVoice 使用作者的 `ASR_POST` / `MIN_EDIT` 前缀。Agentic 的合法尾部 `<KEY>[...]` 单独记录为元数据，正文不含这些标记，原始输出完整保留。全部 60 次正常停止，没有 HTTP 错误或生成截断；这不表示语义全部正确。

### 内存和等待时间

内存列仅为文字模型自身 llama-server 的采样最大值，不含 ASR、桌面客户端或适配服务。MB 为十进制文件大小，MiB 为二进制内存。时间不含模型加载与 ASR；“原生 / 正文”分别对应两组提示。

| 模型 | 权重 MB | 工作集 MiB | 私有提交 MiB | 加载秒 | 短句中位秒：原生 / 正文 | 755 字长段秒：原生 / 正文 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| AgenticASR-Refiner | 688 | 1226（1.20 GiB） | 792 | 1.16 | 0.93 / 1.17 | 9.72 / 8.97 |
| MyVoiceTyping-1.5B | 986 | 1935（1.89 GiB） | 1132 | 1.78 | 1.52 / 1.77 | 13.79 / 14.65 |

Agentic 达到拟定的文件小于 1 GB、工作集低于 1.5 GiB、短句约 1–2 秒的资源目标；MyVoice 在此配置下超过工作集目标。两者都不分配 GPU 层，但推理期间平均约 3.9 个逻辑核忙碌，不能当作对 UE 没有影响。ASR 与桌面仍占显存：整卡整理前至采样最大值，Agentic 为 3587→3598 MiB，MyVoice 为 3507→3507 MiB；11 MiB 波动不能归因给 CPU 模型。

每个输入每组只跑一次，短句中位数来自不同文本；不能把长段 9.72→8.97 秒解释为正文提示加速。加载时间含操作系统文件缓存影响，不是重启后的冷启动。工作集包含映射和共享页面，私有提交不等于驻留 RAM；采样也不等于连续峰值。本轮上下文为 4096，上一轮为 8192，且提示与硬件分配不完全相同，不能把跨轮差值全部解释成模型本身的收益。没有追加 2048 上下文调优或未微调基座对照，因此不能量化微调带来的独立收益。

### 整理效果与原意保留

| 检查 | AgenticASR-Refiner | MyVoiceTyping |
| --- | --- | --- |
| 中英术语 | 本组没有发现正文中英文术语被替换、翻译或臆造 | 原生组保留；正文组将一处 `model` 翻译成“模型” |
| 14 条短文本 | 两种提示的正文逐字相同；4 条有有限实际清理收益；1 条丢失最终速度值 | 原生组 13 条原样复制、AGV 句仅补句号；正文组 12 条复制、AGV 补句号，另一条翻译了术语 |
| 明确改口 | KV Cache“开→关”处理正确；数字“20→12”失败 | 两类改口均保留原口述，没有整理 |
| 引用和状态 | 本组没有执行引用里的指令，也没有把待执行动作写成已完成 | 原样保留，没有执行引用内容 |
| 长段完整性 | 两组均未摘要或截断；12 项人工检查为 11 项通过、1 项部分通过 | 两组长段均与原文逐字相同，事实保留，但没有编辑收益 |
| 连贯正文 | 未按主题分段，数字改口处变得不通顺；一条短文仍输出编号列表 | 保留“嗯”、重复、改口和原来的整块长段，未完成目标 |

这些判断分别报告保真和编辑收益，不合成为一个“准确率”。MyVoice 对已有正确标点和术语的内容选择保留并非错误；问题在于明确带语气词、重复、改口的样本也没有得到整理。本组不能证明它在 ASR 错字纠正任务上无效。

用户 AGV 句的 Agentic 正文为：

> 你把AGV的blueprint给我导入UE，然后把空间的坐标标一下，跑一下transition，看看运动变化

它删掉了“那个”，保留导入对象、目标、坐标标注和运动观察，但“给我／一下／看看”等口语形式仍在。MyVoice 只在用户原句末尾补上句号。两者都不是用户期望的充分书面化结果。

Agentic 对“先开 KV Cache，不，还是先关掉 KV Cache，只在长序列那组再开。短序列现在不要动。”则正确整理为“先关掉KV Cache，只在长序列那组再开。短序列现在不要动。”这是保留最终决定、删除已撤回动作的实际收益。MyVoice 两组仍逐字复制这句原文。

最关键的失败来自 `text-numbers-02`。原文是：

> 我们先试 v0.4.0，batch size 是 16，显存上限 6 GB。不是每秒 20 个，是每秒 12 个，这个数字还要复测。

Agentic 两组都输出：

> 我们先试v0.4.0，batch size是16，显存上限6GB。这个数字还要复测。

最终“每秒 12 个”完全丢失。这不能算合理删除口头修正，也不是增加格式检查就能宣布保真的结果。

长笔记中，Agentic 保留了明天上午、周五只是期望、未验收状态、合并前提、动作顺序、长／短序列区别，以及 `frame pacing` / `meshlet culling` 的待确认歧义。速度句则分别变为：

- 原生：“原先想把速度设成每秒12个，执行这只是试跑设置，尚未复测，不是吞吐量结论。”最终执行意图不清，语法变差。
- 正文：“原先想把速度设成每秒12个，不对了，先按每秒12个执行。这只是试跑设置，尚未复测，不是吞吐量结论。”保住最终 12，却把“20→12”整理成“12→12”，改口未正确消解。

因此，长段的第 4 项只记部分通过；其余 11 项通过不能掩盖这个问题。额外正文提示没有修复短句遗漏，也没有带来自然分段或明显更流畅的表达。

MyVoice 的正文组还将本来可直接使用的“请保留 Unreal 中现有的 shader 设置，并记录这次 model 导入的结果。”中的 `model` 改为“模型”。动作含义基本保留，但不满足保留英文术语原词的要求；原生组没有这项变化。更长的提示不能直接视为质量增强。

### 对下一版的决定

Agentic 保留为首选研究候选，暂不自动替换应用的整理模型。下一步只围绕有实际价值的两个缺口验证：数字／否定／条件改口是否忠实，以及完整长段是否能变成自然正文。应使用新的独立口语材料，不在这 15 个输入上不断堆提示或为“12”加专门规则；若试验更强的去口语要求，要同时检查删减与编造，不能只看读起来顺不顺。

MyVoice 当前不作为正文整理候选继续投入：占用更高，现有两组下没有相应收益。它仍可另作最小错字修正任务的候选，但那需要不同的数据和验证，不计作本次目标已完成。两款都不够资格成为无审阅自动输入的默认层；应用现有原文对照与笔记预览仍有必要。这一比较阶段只增加测试工具、固定协议与记录；随后按用户要求交付本地试用版，变更见下一节。

## 一次有限调优与本地试用交付

用户明确要求限制提示工程：只做必要对比，然后让应用可以开始实际使用。因此本轮只试一个简短、通用的正文要求，没有针对任何数字、术语或用例写替换规则，也没有进行第二次提示调整。**结果没有显示值得部署的改进，候选不采用；应用接入轻量 Agentic 的作者原生协议，工作重点转为可靠的试用流程。**

## 准备真实录音清单

将 [音频清单模板](../tests/fixtures/dictation/manifest.audio.example.jsonl) 复制到本地 `outputs/dictation-data/manifest.jsonl`，并替换占位内容。日常音频不会自动收集到这里。`outputs/` 已被 Git 忽略；评测正文仍是私人数据，不随发布包分发。

每行是一个 JSON 对象：

```json
{"id":"short-001","split":"dev","source":"user_recorded_audio","audio":"audio/short-001.wav","language":"auto","reference":"嗯，把 AGV 的 blueprint 导入 UE，然后跑 transition 看看运动变化。","expected_terms":[{"text":"AGV"},{"text":"blueprint"},{"text":"UE"},{"text":"transition"}],"review_checks":["保留导入方向及观察运动变化的目的"]}
```

- `id` 必须唯一，`split` 为 `dev` 或 `test`。默认只运行 `dev`，冻结集用 `--split test` 显式选择。
- `audio` 相对清单所在目录，也可以是绝对路径；`reference` 是人工核对的忠实转写，保留填充词、自我修正等实际说过的内容。音频不存在时提前报错。
- 单独测试整理时，用 `text` 替代 `audio` 和 `reference`。两种来源只能选一种。文本 case 不计算 ASR 错误率。
- `expected_terms` 在看模型输出之前标注，仅供评测计分，绝不发送给模型。`text` 为规范词形，`count` 为出现次数，默认 1；`equivalents` 是预先允许的等价写法。大小写和空格默认有区别。词表别名不会自动作为正确答案。
- `final_expected_terms` 可单独规定整理后的术语及次数，例如删除重复或完成口头修正后不应保留被撤回的词。省略时沿用 `expected_terms`。
- `review_checks` 记录必须保留的意思、否定、数字、条件、确定性、笔记要点等。它们只供人工评审，不发给模型。

默认评测不需要词表文件。只有额外验证专名辅助时，才使用与应用格式一致的独立 JSON 数组，例如：

```json
[{"text":"ProjectOrchid","aliases":[],"description":"团队内部项目的规范拼写。"}]
```

不从预标注答案自动生成词表，也不要求使用者不断收录每次出现的新词。可选专名消融实验可固定同一个 `--terms` 文件，在对照中关闭两个词表开关，以保持“词表内／外”的分组一致；这一组实验不能取代完全不传词表的主验收。

先按规划收集约 40 条短句及 5 段笔记开发素材，再冻结独立的 20 条短句和 5 段笔记验收素材。数量只是起始规模，不删除困难样本来达标，也不靠反复查看冻结集调提示词。

真人录音应覆盖以下场景，使用本人平时的发音、语速和麦克风，不为了模型刻意逐字朗读英文：

- 常见计算机、图形、游戏引擎、模型与代码讨论中的中英混说，范围超出已经提供的 7 个词。
- 未在应用词表、固定提示或开发样例中登记的常见术语，以及自然讲述中第一次出现的新术语；冻结验收中的具体词形不能提前写进识别上下文。
- 中文句子中连续插入多个英文词、字母缩写，以及一段中文接一小句英文再切回中文；保留自然的中文口音、连读和停顿，不将“英语标准朗读”当作唯一条件。
- 按英语发音说出的名称、带中文口音的英语名称和约定俗成的音译说法。人工参考需预先确认说话人意图及允许的规范写法；无法确认的歧义单列，不能看到输出后补充等价答案。
- 相似发音的普通中文词、词表外的名称、数字、否定和临时口头修正，检查模型是否为了命中术语而误改周围内容。
- 一段包含多个新概念的自然笔记口述，检查长段中的前后术语、条件和待办是否仍一致。

真正不公开的项目代号或自创缩写单列为专名场景，可额外测试少量上下文辅助；其成绩不与无词表的常见术语门槛混算。新增的真实录音、参考文本与分组应由使用者主动提供和确认，不生成假录音补齐数量，也不把重复读同一句当成更多独立场景。

在仓库根目录的 PowerShell 中使用现有 Python 环境。先检查素材；这一步不连接任何服务：

```powershell
.venv\Scripts\python.exe scripts/evaluate-dictation.py tests/fixtures/dictation/cases.text.jsonl --validate-only
```

运行前通过应用准备需要的本地模型。ASR 与文字接口默认同为 `http://127.0.0.1:8001`；`--asr-url` 可更改，`--text-url` 默认跟随它，也可单独覆盖。仅接受本机 HTTP 地址。服务返回文字模型未安装时会停止，不替使用者下载。

示例模型名称和 `--config` 都要替换为本次实际配置。`--state warm` 表示操作者已确认预热，脚本不会替使用者进行隐藏的预热请求：

```powershell
.venv\Scripts\python.exe scripts/evaluate-dictation.py tests/fixtures/dictation/cases.text.jsonl --mode clean --text-model "实际整理模型、量化、revision" --config "实际运行时、prompt版本、硬件及推理配置；空词表" --state warm --repeat 3 --output outputs/eval-clean-empty-terms
```

笔记测试复用同一清单，改为 `--mode notes` 和新的输出目录。原文对照用 `--mode raw`，不请求整理模型。

真实录音的首要 ASR 基线，同样不传词表：

```powershell
.venv\Scripts\python.exe scripts/evaluate-dictation.py outputs/dictation-data/manifest.jsonl --mode raw --asr-model "实际ASR模型、量化、revision" --config "实际运行时、硬件及推理配置；空词表" --state warm --repeat 3 --output outputs/eval-asr-empty-terms
```

先在空词表基线上加 `--mode clean --text-model ...` 测完整日常输入，再用 `--mode notes` 测笔记。需要额外研究专名辅助时，另传专名 `--terms` 文件，分别打开 `--asr-terms` 或 `--processing-terms`，并使用新输出目录。每次只改变一个因素，不把“开启词表后通过”记作空词表门槛通过。

`--output` 必须显式指定一个不存在的目录，避免覆盖以前的结论。`--timeout` 默认每个 HTTP 请求 180 秒；超时、HTTP 错误等逐例记录，失败不会被当成模型输出，运行结束有失败则返回退出码 1。脚本不自动重试请求，以免把第二次请求误记为第一次或隐藏失败率。

## 自动指标的含义

ASR 只拿 **原始转写** 与逐字参考比较。所有一般文本错误指标先作 Unicode NFKC 归一化及大小写折叠，不计普通标点；术语指标保留大小写、空格，因此仍会发现 `UE` / `ue` 等规范词形问题。

| 指标 | 计算口径 | 局限 |
| --- | --- | --- |
| `cer` | 字母、数字和汉字逐字符计算 Levenshtein 编辑距离 / 参考字符数 | 一个长英文词错误可能贡献多个字符错误 |
| `han_cer` | 仅抽取汉字字符后计算编辑距离 | 英文或数字位置变化不可见，不能单独作为质量结论 |
| `latin_wer` | 含 ASCII 字母的连续词及版本标识作为词；逐词编辑距离 / 参考词数 | 这是中英混说里的拉丁词子集 WER，不是整句英文 WER；不评价中文上下文 |
| `mixed_token_error` | 汉字单字、英文/数字连续词作为 token，计算编辑距离 / 参考 token 数 | 中英混合的显式口径，不能直接与采用其他分词规则的论文 WER 比较 |
| 术语命中率 | 规范词形与预定等价形式的匹配数量，上限为标注次数，除以标注总次数 | 仅为自动词形筛查；无法确认命中位置和含义，必须人工检查上下文 |

一般错误率按全部已返回原始转写的参考单位总数汇总，而非对每句百分比直接平均；编辑距离允许错误率大于 100%。参考中没有某类单位时其单条比率为 `null`。词形匹配在 ASCII 单词边界上判断，避免把 `UE5` 当成 `UE`；中文紧邻术语不影响匹配。

术语分别输出 `raw_terms` 与 `final_terms`。主验收没有提供词表，因此预标注术语都落在 `outside_vocabulary`；这不是缺陷，而是要验证的默认使用条件。可选专名实验才按提供词表的规范名称分成内外两组，即使关闭词表开关也保留该分组。额外出现的次数保存在 `observed`，自动命中率不会惩罚幻觉、错位置、否定翻转或漏掉别的内容；不能把命中率称为完整语义准确率。最终整理结果不计算 CER/WER，因为合理改写不等于识别错误。

失败数、原始与最终输出数一起报告；整理失败时仍保留原始转写，但不会把回退原文当作成功整理。质量汇总包含各次重复运行，重复次数不是独立样本数；对冻结集的人工结论按独立原始样本统计。

## 延迟与冷热态

`run.json` 记录模型标识、配置标签、词表和清单 SHA-256、运行参数、模型健康状态和 `cold/warm/unknown` 标签。模型标识与配置标签由操作者填写，应包含量化、固定 revision、运行时版本、整理提示版本、线程/GPU 设置及硬件。健康状态是服务端返回的补充证据，不自动修改操作者的标签。

每例记录 HTTP ASR、HTTP 整理、服务端返回的推理/整理耗时及串行总请求耗时。HTTP 耗时包含序列化、传输及服务内部等待，不能据此单独推导桌面队列时间。按文本、0–15 秒、15–30 秒和更长音频分别汇总成功请求的 p50 / p95，采用 nearest-rank 分位数，并报告 n；少量样本的 p95 常等于最慢的一次。

- 热态：由操作者先通过应用完成预热，再跑 `--state warm --repeat 3` 或更多次；服务是否实际上已热由操作者确认。
- 冷态：`--state cold` 只允许一条 case、一次运行；操作者在应用之外明确重置需要测量的服务后，保证这是该状态下的第一个评测请求。脚本不执行重启。ASR 服务自身可能在接收请求前已经预热，此时该标签只能解释为“服务重启后的首请求”，不能声称测到了完整模型冷启动。
- 未确认状态时使用 `--state unknown`，不能混入冷热态对比。加载和应用启动时间、显存峰值、完整说完至交付时间仍需单独测量。

## 人工验收

每次运行保存 `run.json`、`cases.json`、`terms.json`、`results.jsonl`、`summary.json` 和 `review.csv`。这些文件包含用户主动提供的正文，**不写入日常诊断日志**。CSV 使用带 BOM 的 UTF-8，便于在表格软件查看。

`review.csv` 故意不自动给语义和笔记打通过标记。评审时隐藏模型/配置，交错比较不同运行结果，并填写：

- `raw_required_edits` / `final_required_edits`：分别修到可直接使用且忠实原意的必要字符插入、删除、替换总量，不要求改成同一范文。只在原文确需修改的独立样本上计算下降比例；原本无需修改的句子单独检查不退化。
- `serious_semantic_error`：是否新增数字、否定、条件、确定性、技术含义等严重错误。即使正文通顺也必须检查。
- `all_key_points_preserved`：完整口述的关键要点是否全部保留，有无新增事实。
- `notes_structure_usable`：笔记是否无需重写主体结构即可保存；轻整理样本可留空。
- `reviewer_notes`：术语位置错误、漏项、重复、错改普通词等具体问题。

脚本不会用词相似度替代语义审查，也不会根据示例的关键词命中宣布产品达到 95% 术语准确率、编辑量下降 30% 或笔记验收通过。无词表的常见及未登记术语门槛、自然口音切换、轻整理与笔记应分别报告；只有可选词表实验改善时，不能宣称日常零维护体验已达标。取得个人真实录音、冻结集、人工审阅以及桌面链路验证之前，这些目标仍待验证。
