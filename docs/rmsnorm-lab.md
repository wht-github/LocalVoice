# RMSNorm 单项实验

这个实验只比较两项：**Qwen 原始 PyTorch RMSNorm**，以及**你编写的 TileLang RMSNorm**。不叠加 CUDA Graph、解码循环改造、量化或其他算子优化。暂不修改桌面服务或模型。

## 运行方式

在项目根目录的 PowerShell 中运行：

```powershell
# 不需要完成练习，先运行原始基线
.\rmsnorm-lab.ps1 --baseline

# 完成练习后，先检查正确性
.\rmsnorm-lab.ps1 --check-only

# 正确性通过后，测原始实现与 TileLang 的对照
.\rmsnorm-lab.ps1
```

每次自动保存独立的 JSON 报告到 `outputs/rmsnorm/`，也可用 `--output outputs/rmsnorm/my-result.json` 指定文件。默认比较命令必须先通过全部正确性检查才会计时，不会为错误的实现报告加速比。

## 你修改哪个文件

只需修改 `experiments/tilelang/rmsnorm_exercise.py` 的 `rmsnorm_kernel`。框架已经提供形状声明、每行一个块、每块 128 个线程和输出包装。

当前起始实现只是 `X * W`，能够编译，但有意缺少归一化。运行比较时会在 `constant_1` 报 `RMSNorm exercise not correct yet`，这是尚未完成练习的预期结果。

三个 TODO 对应：

1. 将输入转换为 FP32，计算每个元素的平方。
2. 将一行 1024 个平方值归约为一个总和，再除以 1024 得到均值。
3. 加上 `1e-6`，求平方根的倒数，用它缩放原始输入；先转换为 FP16，再乘权重。

文件内提供了 fragment 缓冲区和 `T.reduce_sum` 的提示。先保持宽度、线程数和 epsilon 不变，把公式写对。

## 基线与输入

`rmsnorm_reference.py` 忠实保留当前 Transformers 5.16.1 的 `Qwen3RMSNorm.forward` 计算顺序。准备框架时，已与安装环境中的实际 Qwen3RMSNorm 在 8 组输入上做零容差比较，结果完全一致。

输入来自模型性能分析中观察到的**形状**，测试数值由固定随机种子及边界值构造，并非从录音中导出的真实激活：

| 阶段 | 输入形状 | 权重形状 | 数据类型 |
|---|---|---|---|
| 单 token 解码 | `[1,1,1024]` | `[1024]` | FP16 |
| 示例录音的 prefill | `[1,151,1024]` | `[1024]` | FP16 |

两种输入都按行独立计算，最后一维固定为 1024。prefill 的 151 是该录音的测量值，不是模型所有录音的固定长度。

## 正确性检查

每种形状检查 7 类输入，共 14 组：零、常量、随机值、极小值、大幅值、不同行的不同幅值、全零权重。普通权重包含不同大小的正负数，避免全 1 权重掩盖实现错误。

框架检查输出形状、设备、类型、有限值，以及相对原始参考的数值误差，报告最大和平均绝对误差。初始阈值 `rtol=2e-3, atol=2e-3` 用于 FP16 算子练习，不意味着自动通过完整 ASR 的质量验收。

大幅值用例可发现误用 FP16 计算平方导致的溢出；极小值检查 epsilon；不同行的不同幅值检查是否错误地跨行归约。框架还以 FP64 计算公式、保留中间 FP16 舍入的方式检查 PyTorch 基线。

## 怎样解读计时

两种实现都接收相同输入和权重，返回新分配的输出。参考保持原始中间张量操作；TileLang 包装也把输出分配计入时间。

预热 20 次后，测 7 组、每组 100 次，计时前后等待 GPU 完成。报告单次平均耗时的中位数和范围；**包含输出分配、Python 调度和 GPU 执行**，排除首次编译，不是 GPU 内核纯时间。`speed_ratio` 大于 1 才表示这个调用范围下 TileLang 更快。

已有基线成功运行。等你的实现通过检查，再在同一进程内重新比较两种实现；不要只拿今天的基线数字和另一天的结果相除。后续若接入 Qwen，也只替换 RMSNorm，其他设置全部维持原始版本，单独评估这项改动。
